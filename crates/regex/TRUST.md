# What verilith-regex trusts, and why

Verus checks every proof in verilith-regex, but a proof only means something
relative to the definitions it starts from and the tools that check it.
This file lists everything that is assumed, not proven.

## The short list

- **Tools**: Verus (version pinned by the `vstd` version in `Cargo.toml`),
  Z3, rustc.
- **vstd**, and from the sibling crates only definitions: `verilith_core::utf8`'s
  `utf8_len` and `utf8_from` (well-formed UTF-8, Unicode Table 3-7) and
  `verilith_text::utf::spec::dec8_at` (the code point of a sequence). verilith-core's
  `utf8_valid_scalar` is called to validate the pattern; it is verified in
  verilith-core against `utf8_from`.
- **Specifications to read**: `src/spec.rs` (what a regular expression
  matches), `src/syntax.rs` (what a pattern means) and the set definitions
  in `src/data.rs`. The theorems say the code computes these. Whether
  these say what you want is for a reader to judge.
- **The Unicode tables**: `src/tables.rs` and the seven accessors in
  `src/data.rs`.
- **SIMD instructions**: the specifications of the instructions the
  first-byte scans use. On x86-64, verilith-simd's specifications of six
  SSE2 instructions (load 16 bytes, splat, compare bytes, subtract
  stopping at zero, or, movemask), under its proven `sse2` wrappers, which
  `src/lanes.rs` re-exports. On AArch64,
  verilith-simd's NEON specifications (`vld1q_u8`, `vdupq_n_u8`, `vceqq_u8`,
  `vqsubq_u8`, `vorrq_u8`, and those under its verified `nibmask16`),
  its slice load, and its `has_neon` CPU check. The scans built from
  them (`src/find.rs`) are proven. `tests/api.rs` also checks
  it at every offset.
- **Unverified code**: `src/capi.rs` (the C API), the two-line
  `Regex::captures_at` wrapper in `src/lib.rs`, and tests and tools.
- **Not modelled**: stack depth, allocation failure, and the capacity of
  vectors.

`scripts/verify.sh` fails if `assume` or `admit` appears anywhere, or
`external_body` outside `src/data.rs`.

## The specifications

`src/spec.rs` is 220 lines. It was written to be read, and to be
independent of how the matcher works: it does not mention programs,
threads or automata. The things in it most worth checking:

- `ms` for `Plus`: the loop rule. The first iteration may match the empty
  string, and then the loop ends; a later iteration counts only if it
  consumes at least one byte. This is where verilith-regex differs from RE2 in
  rare nested cases (README, "Differences from RE2").
- `Re::Char` and `dec`: a class matches one well-formed UTF-8 sequence.
- `look_holds`: `\b` is about ASCII word characters, `(?m)` lines end
  at `\n` only.
- `search`: leftmost start first, then the best match at that start.

`src/syntax.rs` is longer (about 950 lines) because RE2's syntax is large.
It is a reference parser, so it can be compared with RE2's documentation
construct by construct. It was also compared with RE2 itself: `tests/diff`
runs RE2 and verilith-regex on random patterns, a third of them random strings of
syntax characters, and they agree on which are valid.

## The Unicode tables

`src/tables.rs` holds the general category and script ranges and the case
folding pairs. It is generated by `tools/gen_tables.py` from RE2's own
tables, and `scripts/check_tables.sh` checks that. The proofs treat the
tables as uninterpreted functions (`group_lo`, `group_hi`, `fold_a`, ...),
so the theorems hold whatever the tables contain: what `\p{Greek}` means
is "the ranges the table lists for Greek". That the tables are Unicode's
is trusted to RE2 and the generator.

The seven `*_at` functions in `src/data.rs` are `external_body`: each is
one bounds-checked array read, `TABLE[i]`, specified to return the
uninterpreted function at `i`. They are trusted because Verus cannot yet
read large constant arrays; nothing else in the crate is `external_body`.
Compile-time assertions check each table's length against the constant
used in the accessor's precondition.

## The compiler's output needs no run-time check

The matcher relies on three properties of the program it runs: every jump
that consumes no input goes forward (which is what makes its closure
terminate within its bound), every jump stays inside the program, and
class and slot numbers are in range. These used to be checked each time a
pattern was compiled, with `Regex::new` returning `TooBig` if the check
failed, and it was only tested, not proven, that the check never fails.

They are now proven for every program the compiler emits, and the check is
gone. `compile::lemma_compiled_fwd` proves the first two for the
compilation scheme's program (`code_n` followed by `Match` and `Fail`), by
induction over the regular expression with `lemma_fwd_n` for the normal
copy of a loop body and `lemma_fwd_z` for its no-progress copies; the
compiler is already proven to emit exactly that program. The emitter
carries the third (`compile::insts_ok`) from the syntax tree, whose class
and group numbers are bounded. So `compile::compile` returns a program
that meets `Prog::wf` for every pattern the parser accepts, and
`Regex::new` returns `TooBig` only for a pattern over a size limit.

## Unverified code

`src/capi.rs` turns C pointers and lengths into slices, calls
`Regex::new` and `Regex::search_with`, and copies results out. It must
meet the preconditions of the verified functions it calls:

- `search_with` needs `from <= text.len() < usize::MAX`: checked there.
- `search_with` needs working memory made for the same pattern: each
  handle keeps its own pool, and never passes it to another pattern.

It also holds logic of its own, which is tested and not proven: the
`cre2_*` options (which put `(?i)` or `(?s)` in front of the pattern, or
quote it), and anchored matching. A search anchored at the start runs
the verified search and accepts the match only if it starts at the
start position. That is right because the verified search reports the
match at the leftmost start, and at one start the same match as an
anchored search. A search anchored at both ends runs the verified
search for `(?:pattern)\z`. `tests/capi/run.sh` compares all of this
with cre2 and RE2.

## Not modelled

- **Stack depth.** The parser recurses once per nested group (at most
  250), and the compiler and the tree's destructor recurse over the
  syntax tree (height at most 4096). The matcher does not recurse.
- **Allocation.** Running out of memory aborts.
- **Vector capacity.** The memory theorem bounds the lengths of the
  matcher's lists (at most one entry per instruction). `Vec` may
  reserve up to twice that.
- **Time.** The step bound counts loop iterations of the matcher. Each
  iteration is a bounded number of machine operations, but that last
  step is an argument, not a theorem.
