# libexpat's tests that fail against verilith-xml's expat ABI, and why
# (scripts/test-expat.sh fails on any failure not listed here, and on any
# listed test that passes). One per line: suite, test, reason, separated by
# tabs. The reasons (crates/xml/README.md, "The expat C ABI", has more):
#
#   allocator               the parser's own memory comes from Rust's
#                           allocator, not the XML_Memory_Handling_Suite
#                           (which XML_MemMalloc and content models use), so
#                           a failing allocator does not fail the parse
#   internal                tests of libexpat's internals (its hash table,
#                           tokenizer, accounting), stubbed in
#                           tests/c/expat_internals.c
#   utf16-without-bom       UTF-16 input without a byte order mark, which
#                           XML 1.0 (4.3.3) requires; expat accepts it
#   incremental             the document is checked whole, when the final
#                           buffer arrives: no handler runs, and no error is
#                           found, before then; buffer limits differ
#   external-dtd            the external DTD subset and external parameter
#                           entities are not read
#   encoding                encodings: UTF-8 checks that expat makes
#                           differently, unknown-encoding handler details
#   default-handler         markup reported to the default handler: DTD
#                           declarations and white space in the prolog are
#                           not reported
#   amplification           expat's input-amplification accounting (there
#                           is none: expansion is lazy and parsing linear)
#   error-code              a rejected document gets another error code or
#                           position than expat gives it
#   fifth-edition-names     names allowed by XML 1.0 Fifth Edition, which the
#                           suite's older tests reject (as expat does)
#   error-not-read          the error is in the external subset, an external
#                           entity or a parameter entity, which are not read
#   fails-with-libexpat-too fails the same way with libexpat 2.10.0 (the npm
#                           package of the suite has CR LF line ends in places)
